Transactions et synchronisation
Préférences et shared_data_revision sont validées dans la même transaction.
Le moteur commun conserve le verrou anticipé, les savepoints et les transactions
externes. Les versions publiques et instantanés avancent au commit réel seulement.
Les versions en attente permettent deux sauvegardes dans la même transaction ;
une annulation ne prête pas sa version à une transaction ultérieure. Échec du
signal : données annulées, ancienne version utilisable pour une reprise explicite.
Une sauvegarde sans changement n'émet aucun signal ; un contexte inchangé peut
être sauvegardé sans SQL même s'il est désormais périmé, puisqu'il n'écrit pas.
Le polling existant des postes reste inchangé, à intervalle de 10 secondes ; il
reporte ses rafraîchissements pendant les saisies/modalités protégées. Il ne s'agit
pas d'une garantie de mise à jour instantanée d'un champ en cours de modification.

Limites et suite
1. Pas de PC de travail ni partage SMB réel disponible. Ces preuves concernent
   MySQL local et des clients indépendants ; les lettres réseau, UNC, ACL et
   interruptions SMB restent à valider sur site, sans redemander leurs chemins ici.
2. Les vieux exécutables et outils SQL directs peuvent contourner les contrôles.
   Prévoir une version homogène lors d'un futur packaging explicitement autorisé.
3. Thème/colonnes, préférences partagées et transition métier du mois ne forment
   pas une transaction distribuée unique. Une opération combinée peut enregistrer
   les préférences avant l'échec d'un changement de mois ; vérifier l'état réel
   puis recharger avant de recommencer. Les méthodes métier de mois restent à
   auditer séparément pour les changements explicites simultanés, sans déclarer
   cette correction suffisante pour toutes les transitions possibles.
4. Le document workspace est versionné en bloc ; pas de fusion champ par champ.
   Les empreintes comparent l'état ; un aller-retour exactement aux valeurs initiales
   n'est pas distingué. Un compteur historique nécessiterait un lot de schéma dédié.
5. En panne centrale, l'affichage local et le repli d'identité legacy restent
   possibles ; ils ne permettent pas de sauvegarder un workspace sans version.
6. Interblocage ou acquittement perdu du commit : vérifier l'état avant toute
   nouvelle tentative. Aucun rejeu automatique des opérations métier ajouté.
