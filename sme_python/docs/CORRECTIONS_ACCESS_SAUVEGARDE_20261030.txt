L9-01 — P1 CONFIRMÉ : IDENTITÉ DES NOUVEAUX AGENTS APRÈS ACCESS

Emplacements :
src/sme_gend/services/access_identity_map.py:62 (write_identity_map)
src/sme_gend/services/access_identity_map.py:35 (read_identity_map)
src/sme_gend/services/mysql_bundle_export_to_access.py:354 (_write_liste_generale)

src/sme_gend/services/mysql_bundle_import.py:132 (copy_referentials_and_satellites_to_mysql)

Cause : l'identité interne GEN-APP-... ne tient pas dans le champ LONG Id du
gabarit Access. L'ancien export tentait ce texte puis réinsérait sur une autre
connexion après toute erreur. Le gabarit officiel impose aussi un Id explicite,
sans AutoNumber. Une identité numérique réimportée pouvait créer un deuxième
agent, notamment sans matricule ; le test MySQL avant correction l'a reproduit.

Correction : réserver les anciens Id, attribuer des numéros disponibles aux
seuls nouveaux agents dans le fichier exporté, puis ajouter la table facultative
locale SGI_AgentIdentity (AccessId, InternalKey). Les agents MySQL conservent leur
clé durable ; les anciens Id Access ne sont ni renumérotés ni remplacés.
L'import de la liste et des huit familles satellites traduit la même identité.
Les correspondances invalides, ambiguës ou dupliquées et les tables dont le type
ODBC annoncé n'est pas TABLE sont refusées.
La liste et ses correspondances sont lues avant la purge du mois existant.
Les archives anciennes sans cette table conservent leur lecture habituelle.

Vérification : réimport sans matricule dans MySQL, huit familles de clés
satellites en tests unitaires, et cycle réel MySQL → MDB ACE → MySQL. Aucun agent
supplémentaire ; les fiches mission/maladie/stage restent rattachées à leur agent.
Une correspondance corrompue est refusée avant la purge : carrière et mission
du mois synthétique restent présentes. L'identité servant aux noms de photos
reste stable ; ce dernier contrôle porte sur la clé, pas sur un affichage réseau.

L9-05 — P1 CONFIRMÉ : FIDÉLITÉ ET COHÉRENCE DU REPLI SQL

Emplacements :
src/sme_gend/services/mysql_backup_service.py:57 (_python_sql_dump)
src/sme_gend/services/mysql_backup_service.py:42 (_literal)
src/sme_gend/services/backup_sql.py:86 (validate_restore_statement)

Cause : conversion de bytes via str() et accumulation du dump entier en mémoire.
La cohérence des lectures dépendait implicitement de l'isolation de connexion,
sans garantie explicite de cliché (risque si READ COMMITTED est configuré).
Un Id auto-incrémenté égal à zéro
pouvait aussi être réattribué pendant la restauration.

Correction : une transaction REPEATABLE READ WITH CONSISTENT SNAPSHOT, lecture
en flux avec SSCursor ; identifiants SQL protégés et sérialisation fidèle des
octets, textes UTF-8, décimaux et dates. NO_AUTO_VALUE_ON_ZERO préserve les Id
zéro. Le dialecte de restauration accepte ces seules nouvelles formes sûres ;
les instructions SET GLOBAL et expressions étrangères restent refusées.
Le mode de session du pool est restauré et le cliché de lecture est annulé.
La sauvegarde refuse une transaction d'écriture active qu'elle pourrait valider.

Le repli refuse les vues, routines, déclencheurs, événements et tables non InnoDB
qu'il ne peut sauvegarder fidèlement. Le client natif est nécessaire pour les
objets SQL avancés ; les tables non transactionnelles sont refusées aussi avant
le dump natif, faute de garantie de cohérence. Ce refus bloque ensuite la clôture.

Vérification native : restauration exacte de bytes 00ff, binaire vide, accents,
sauts de ligne/guillemets/antislash, décimal, date et Id zéro. Une autre connexion
modifie deux tables pendant l'écriture du dump : les deux tables restaurées
présentent le même état antérieur. Le refus du repli sur vue/MyISAM est testé,
sans publication SQL ni altération des données sources.

Performance : la sauvegarde ne conserve plus toutes les lignes ni tout le texte
SQL en mémoire. Aucun gain chiffré de temps ou de mémoire n'est revendiqué : ce
lot n'a pas établi de benchmark volumétrique avant/après comparable.

Aucune migration du schéma MySQL n'est requise et aucun identifiant existant

exportée. Les anciens outils peuvent ignorer cette table ; s'ils la suppriment,

de restauration applicative. La restauration du dialecte interne est aussi
testée via l'exécuteur dédié. Aucun outil n'est lancé sur la base réelle ici.

Pour revenir sur les sources, conserver d'abord l'état courant et comparer le

LIMITES ET PROCHAINS LOTS

1. La restauration complète DROP/CREATE reste non atomique, selon la décision
   métier antérieure. La sauvegarde préalable et les erreurs explicites sont
   maintenues ; une bascule de restauration sûre reste un chantier distinct.
2. La clôture comprend encore plusieurs transactions de statut/session après
   le backup. Ce lot sécurise son préalable, sans prétendre rendre toute la
   transition atomique ni empêcher toutes les saisies après le début du cliché.
3. Les sauvegardes transactionnelles supposent l'absence de DDL concurrente
   (ALTER/CREATE/DROP/RENAME/TRUNCATE). Prévoir une fenêtre sans migrations ;
   le cliché InnoDB protège les écritures de données concurrentes testées.
4. L'archive SQL contient les données métier et comptes applicatifs sauvegardés.
   Elle n'est pas chiffrée : les droits/rétention du dossier d'archives restent à
   administrer. La correction ne promet pas une résistance aux administrateurs
   de la machine ni une durabilité contre toute panne matérielle.
5. À confirmer sur deux postes réels : visibilité des photos sur le partage UNC,
   droits Windows et rafraîchissement multi-poste. Le test de ce lot vérifie la
   stabilité des identités photo ; il ne simule pas un partage SMB distant réel.
6. TLS MySQL avec validation de certificat reste à déployer. L'encodage de
   certains mots de passe non ASCII échoue encore dans la connexion PyMySQL
   existante (constat reproduit sur compte synthétique). Unifier cet encodage
   exige une validation transversale de compatibilité des comptes ; non modifié.
7. Le format Access ancien ne représente pas tous les champs/historiques du
   dossier RH moderne. La correspondance d'identité ne rend pas cet export
   équivalent à une sauvegarde complète MySQL, photos et paramètres.
8. Aucun exécutable généré : les corrections présentes dans les sources ne sont
   pas incorporées à l'ancien portable. Ses empreintes ont été contrôlées.
