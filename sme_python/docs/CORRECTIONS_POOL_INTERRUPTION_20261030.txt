L17-01 — P1 confirmé — transaction interrompue validée par l'opération suivante
Emplacement : mysql_pool.py:304 (pooled_connection).
Cause racine : les gestionnaires except Exception ne traitaient pas les sorties
KeyboardInterrupt, SystemExit et GeneratorExit. Le worker Qt intercepte pourtant
BaseException et peut continuer à fonctionner après l'échec de la tâche.
Sur le thread principal, la connexion conservait la transaction ouverte ; le
commit de l'opération suivante validait aussi la saisie abandonnée. Dans un
worker, la connexion empruntée restait hors file avec sa transaction ouverte.
Reproduction native avant correction : INSERT 1, interruption, puis INSERT 2 ;
SELECT retournait (1,2) au lieu de (2) sur le thread principal. Dans le worker,
SERVER_STATUS_IN_TRANS restait positionné sur la connexion abandonnée.
Correction : traitement de toutes les sorties exceptionnelles pour le seul
nettoyage transactionnel ; rollback puis propagation de l'interruption originale.
Les connexions de fond concernées sont retirées et fermées. Une connexion de
lecture interrompue est également exclue de son cache/pool. Aucun corps métier
ni commit n'est rejoué automatiquement.
Tests : 6 cas unitaires écriture, 6 lecture, 6 interruptions de commit ; 6 cas
MySQL natifs sur les deux modes de connexion. Les hooks après commit de l'opération
annulée ne s'exécutent pas ; ceux de l'opération suivante s'exécutent une fois.

L17-02 — P1 confirmé — réutilisation après échec d'annulation
Emplacements : mysql_pool.py:304,
mysql_pool.py:103 (_discard_main_connection).
Cause : un échec de rollback était ignoré et la connexion principale restait
dans son cache. Si elle restait utilisable, le commit suivant validait des
changements qui auraient dû être abandonnés.
Reproduction native : le rollback est défaillant après INSERT 1, la connexion
est toujours ouverte ; une opération distincte INSERT 2 validait les deux lignes.
Correction : retrait immédiat du cache et fermeture de cette connexion. La
prochaine opération en crée une autre. Un avertissement explicite indique
l'échec d'annulation, sans recopier le texte potentiellement sensible du pilote.
L'erreur métier initiale reste l'erreur propagée, même si rollback et close
échouent à leur tour. Une fermeture échouée n'autorise aucune remise dans le pool.
Tests : identité de l'exception, nouveau client au prochain emprunt, absence de
commit sur l'ancienne connexion, retrait même si close lève une autre interruption,
journal sans détail sensible ; un cas natif prouve que seule la ligne 2 subsiste.

L17-03 — P2 confirmé — places de pool et connexions perdues pendant l'acquisition
Emplacements : mysql_pool.py:111 (_BoundedPool),
mysql_pool.py:80 (_new_connection),
mysql_pool.py:234 (_main_thread_connection).
Cause : une interruption durant la création réservait une place sans la rendre ;
une interruption lors du réglage READ ONLY ne fermait pas le nouveau client.
Les contrôles de santé interrompus pouvaient également retirer une connexion de
la file d'attente sans la fermer ni rendre sa place.
Conséquence : après plusieurs occurrences, saturation artificielle du pool,
attentes pouvant atteindre le délai d'emprunt existant et transactions retenues.
Correction : libération de la réservation, fermeture du client en initialisation
échouée, retrait et comptage correct après interruption du contrôle de santé,
y compris après attente d'une connexion rendue par un autre thread.
Tests : création et réglage lecture seule interrompus, contrôles principal/fond,
file déjà disponible ou attente réelle entre deux threads, nouvel emprunt possible.

Performances, compatibilité et limites
La correction rend les places réservées et évite leur saturation artificielle.
Aucun gain de vitesse globale ni benchmark avant/après comparable revendiqué.
Les 30 secondes de délai d'emprunt, la taille maximale, les options de lecture,
les paramètres d'authentification et les règles métier restent les mêmes.
Une annulation réussie conserve la réutilisation normale de la connexion principale.
Les signatures publiques, le schéma et les formats de données sont compatibles.
Le nettoyage n'absorbe pas l'interruption de l'opération : elle est propagée.

Ces gestionnaires s'exécutent quand Python peut dérouler ses contextes. Ils ne
garantissent pas un nettoyage local après panne électrique, arrêt forcé du
processus, corruption mémoire ou terminate() d'un thread. Une connexion fermée
ne peut pas défaire un commit que le serveur aurait déjà validé avant perte de
l'acquittement. Aucun nouvel automatisme de relance n'est ajouté ; les marqueurs
de reprise métier existants restent nécessaires pour les opérations concernées.
Si le pilote refuse aussi la fermeture, la connexion est exclue du pool mais
sa fermeture distante et la libération de ses verrous dépendent du serveur et
de ses délais ; l'avertissement doit être examiné.
La suite existante n'est pas une preuve de couverture exhaustive des modules.
