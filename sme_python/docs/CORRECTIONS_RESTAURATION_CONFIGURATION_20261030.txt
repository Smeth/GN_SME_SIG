L14-02 — P1 CONFIRMÉ : CONFIGURATION SQL VALIDÉE MALGRÉ UN ÉCHEC DE FICHIERS

Emplacements :
src/sme_gend/services/backup_restore_service.py:820 (restore_backup)
src/sme_gend/services/configuration_restore.py:137 (_apply)
src/sme_gend/services/configuration_restore.py:38 (_sql_gate)

Avant : import_config_rows validait sa transaction puis files.publish publiait
les fichiers séparément. Une panne de cette publication conservait les nouveaux
paramètres SQL alors que les fichiers revenaient à leur état précédent.
Le scénario natif d'échec après publication l'a reproduit avant correction.

Correction : le flux sans instructions SQL est délégué à un service coordonné.
Les lignes de configuration, un marqueur d'opération et une nouvelle révision
partagée font partie d'une seule transaction InnoDB. Les fichiers sont préparés
et leurs originaux conservés avant les mutations SQL ; leur publication est
achevée avant la validation de cette transaction. Une exception avant commit
annule les lignes et compense les fichiers sous contrôle de leurs empreintes.

Les paramètres SQL précédents des clés concernées sont conservés dans un fichier
privé configuration_before.json ; les fichiers initiaux, préparés et l'archive
stable sont conservés dans la session de récupération. Aucun contenu de ces
copies potentiellement sensibles n'est recopié dans les messages ou le rapport.

Un verrou de profil sérialise les restaurations de configuration du profil.
Quand MySQL est nécessaire, le service prend le verrou des médias du lot 13
et le verrou de maintenance utilisé par la restauration complète. Une autre
restauration active provoque un refus avant publication. Le moteur app_config
doit être InnoDB ; aucune conversion de table ou DDL n'est exécutée par ce flux.

Les médias sélectionnés sont résolus sous cette coordination à partir du chemin
actuellement actif, sans reprendre un cache ancien. Une bascule attend la fin
de la restauration puis migre ses images restaurées. Un test vérifie la dérogation
locale explicite, un autre vérifie la sérialisation avec une bascule simultanée.

Les restaurations purement locales restent possibles sans MySQL. L'invalidation
des caches ne lance plus indirectement une lecture de contexte ni l'initialisation
de la configuration SQL dans ce cas. Les modules de journaux conservent leur
domaine de verrouillage distinct.

L14-03 — P1/P2 CONFIRMÉ : REJEU D'ÉTAT OPÉRATIONNEL ET COLLISIONS DE CLÉS

Emplacements :
src/sme_gend/services/configuration_restore.py:32 (operational_key)

Une restauration de préférences ne doit pas remettre d'anciennes livraisons de
journaux ni une révision périmée. Les clés shared_data_revision,
migration_v2_complete et les préfixes audit_mirror: et configuration_restore:
archivés sont exclus de ce flux, tout comme shared_personnel_media.
Les demandes de journaux déjà présentes en base restent en place. Une nouvelle
révision configuration_restore est publiée uniquement avec la transaction réelle.

La conservation des comptes protège aussi leur absence : une archive ne crée
pas de comptes quand cette option impose de garder l'état actuel. Quand la
conservation est décochée, le remplacement sélectionné garde son comportement.

Deux tests natifs supplémentaires ont reproduit des collisions de collation :
une variante accentuée de auth_config contournait la conservation, et deux clés
différentes en Python désignaient la même ligne MySQL. Le service filtre les
noms protégés puis les compare selon la collation effective de config_key.
Des clés dupliquées selon cette collation sont refusées avant publication.
Les valeurs SQL restent paramétrées ; le nom de collation provient du serveur
et passe une validation fermée avant son utilisation comme identifiant.

L14-04 — P1 : REPRISE APRÈS INTERRUPTION ET COMMIT INCERTAIN

Emplacements :
src/sme_gend/services/configuration_restore.py:103 (_committed)
src/sme_gend/services/configuration_restore.py:215 (_recover_pending)
src/sme_gend/services/configuration_restore.py:187 (_load_files)
src/sme_gend/services/restore_files.py:44 (add)

Chaque restauration coordonnée possède un marqueur configuration_restore:<UUID>,
écrit dans la même transaction que les paramètres. Le journal local est
synchronisé avant les phases de publication et de commit. Une lecture actuelle
du marqueur, dans une transaction de lecture explicite avec FOR UPDATE, attend
la résolution d'un INSERT/COMMIT/ROLLBACK en vol. Elle ne confond pas une ligne
encore non validée avec une absence définitive. Un test vérifie cette attente.

La preuve ne dépend pas du dernier jeton global : une autre saisie peut le
remplacer sans effacer le marqueur de cette restauration. Un accusé de commit
perdu confirmé par ce marqueur produit ConfigurationRestoreCommittedError,
avec l'instruction de ne pas recommencer. Si l'état ne peut pas être établi,
la session reste à vérifier, les copies sont conservées et le succès n'est
pas annoncé.

Avant une nouvelle restauration sans dump SQL, les sessions incomplètes du
profil sont examinées. Sans commit, les fichiers publiés sont compensés ; avec
commit, la session est finalisée. Cette reprise n'est pas lancée automatiquement
au démarrage de l'application. Il faut conserver la connexion de coordination
et les copies privées pour résoudre une session incomplète.

Les chemins de récupération sont recalculés à partir des composants et des
racines actuelles. Un dossier déplacé, une autre base, un original altéré,
un fichier préparé corrompu ou une destination modifiée depuis la publication
provoque un arrêt pour vérification. Aucun retour arrière ne remplace une
modification externe dont l'empreinte ne correspond plus à la publication.

Une course sur paths.json a également été reproduite : le fichier pouvait
changer entre sa fusion et sa copie de sécurité. RestoreFiles.add accepte
maintenant un cliché attendu ; le service l'utilise pour refuser ce changement
concurrent au lieu de rétablir des chemins lus trop tôt.

Les marqueurs confirmés sont conservés ; leur purge éventuelle est un travail
de rétention distinct, à coordonner avec les journaux de récupération.

LIMITES ET PRIORITÉS RESTANTES

- Ce mécanisme coordonne des transactions et compense des fichiers ; MySQL et
  le système de fichiers ne constituent pas une transaction distribuée. Après
  un arrêt brutal avant commit, des fichiers publiés peuvent rester en place
  jusqu'à la reprise précédant une nouvelle restauration. Les chemins conservés
  réduisent le risque de reconnecter le poste ailleurs pendant cet intervalle.
- La panne électrique, la durabilité du stockage, les ACL et les verrous de deux
  vrais postes SMB ne sont pas validés ici. Une copie de récupération corrompue
  bloque le retour automatique ; elle ne provoque pas un écrasement aveugle.
- Les verrous sont coopératifs. Les anciens exécutables, SQL externes et copies
  manuelles ne sont pas automatiquement raccordés. La restauration complète
  conserve sa fenêtre de maintenance, autres postes fermés. Son mécanisme
  préparé et ses règles de remplacement restent ceux du lot 10.
- Les marqueurs et copies de récupération doivent avoir une politique de
  rétention contrôlée. Le service ne supprime pas massivement ces éléments.
- TLS, les autres écritures non couvertes, les avertissements Qt/Pandas et le
  profilage volumétrique/réseau général restent des chantiers distincts.
