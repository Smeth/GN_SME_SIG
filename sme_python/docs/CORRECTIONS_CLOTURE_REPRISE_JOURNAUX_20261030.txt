Correction : les préférences centrales existantes ne sont pas remplacées par le

La clôture lit ses mois depuis sme_periode, sans réécrire les préférences UI pour

Important : l'import de carrière conserve sa transaction propre, achevée avant

annoncé comme annulé par le mécanisme transactionnel de clôture. Il faut vérifier
son résultat avant de décider de le relancer. Les options d'activation explicite

ensemble ; aucun miroir n'est créé avant le commit. Un échec de copie connu après

actions sensibles et documents en ligne. Les flags de miroir existants restent

La demande ne contient pas de chemin d'écriture arbitraire : type de journal et
mois validé seulement. Les chemins sont résolus par les fonctions de l'application.

L11-04 — P1 : REPRISE IDEMPOTENTE ET LIGNES INTERROMPUES

Emplacements :
src/sme_gend/services/audit_mirror_recovery.py:222 (deliver_key)
src/sme_gend/services/audit_mirror_recovery.py:166 (_repair_tail)
src/sme_gend/services/local_audit_mirror.py:13 (locked_mirror_stream)

Chaque copie porte _mirror_event_id, un identifiant stable. Sous verrou entre
processus, la livraison conserve en base un point de reprise avant d'écrire :
position, identité du fichier et empreinte de son suffixe précédent. Elle relit
normalement ce suffixe seulement ; un fichier remplacé/tronqué provoque une
recherche depuis le début. Les identifiants déjà présents ne sont pas réécrits.
Le même identifiant associé à un autre contenu est refusé, pas écrasé.

Une dernière ligne JSON complète privée de retour à la ligne est conservée et
terminée. Une fin invalide ou coupée au milieu d'un caractère UTF-8 est d'abord
sauvegardée, synchronisée et protégée dans .audit-recovery/<UUID>.part ; seulement
ensuite le fragment est retiré de la fin du journal et les événements manquants
sont réécrits. Les lignes complètes précédentes restent en place.

Les écritures sont synchronisées par flush/fsync avant suppression de la demande
en base. Un arrêt entre écriture et confirmation rejoue la livraison en dédoublonnant
les événements présents. Aucun rejeu de modification métier n'est effectué : la
reprise écrit seulement la copie JSONL et son état de livraison.

Vérifications MySQL + fichiers : panne avant append, append interrompu sur un
octet UTF-8, panne après fsync avant DELETE de confirmation. Après rechargement
du module (aucun callback/état mémoire conservé), la reprise produit une seule
ligne complète contenant les valeurs gelées avant mutation du dictionnaire
appelant. Une seconde reprise ne produit aucune nouvelle ligne.
Le rollback métier ne laisse ni demande ni fichier. Les quatre destinations et
les lots sont testés. Le repli document après accusé incertain garde le même
identifiant et n'est pas ajouté une deuxième fois lors de la reprise.

Une vérification supplémentaire utilise de vrais processus Windows : arrêt
volontaire os._exit(91) après fsync d'une ligne et avant confirmation SQL, puis
deux processus concurrents de reprise sur les 40 demandes du même profil.
Résultat : 40 lignes JSON valides, 40 identifiants distincts, aucun doublon et
aucune demande restante. La base UUID de cet essai est ensuite supprimée.
La preuve est conservée sous native_process_validation.json dans le dossier du lot.

L11-05 — P1/P2 : REPRISE AUTOMATIQUE, PROFILS ET CHEMINS

Emplacements :

recopier le contenu personnel des événements. Les demandes ne sont pas effacées
en cas d'échec. Sans identifiant local existant, aucun accès SQL n'est lancé par

La non-régression a détecté une incompatibilité du premier routage avec un nom

de chemin arbitraire. Les scénarios historiques affectés ont été rejoués avec

VALIDATION DE PRÉPRODUCTION ET EXPLOITATION

1. Avec les sources corrigées sur une copie, clore un mois contenant des données
   et vérifier statuts, date de fin du segment, carrière actuelle, audit et mois
   suivant. Rejouer la même demande : aucune seconde bascule/audit de clôture.
2. Tester les deux options d'import : archiver/fermer sans activation, puis avec
   activation. Un mois historique sans activation ne doit pas déplacer le mois
   courant. Vérifier qu'une fenêtre Réouvert reste conservée.
3. Sur deux postes cohérents en version, confirmer que les autres postes voient
   le changement après le signal partagé. Les anciennes versions contenant la
   migration locale non protégée peuvent encore altérer le mois ; ne pas les
   mélanger à une validation de ce mécanisme.
4. Avec les miroirs activés, rendre seulement leur destination indisponible sur
   un dossier synthétique. L'événement MySQL doit rester enregistré avec une
   demande en attente. Ne pas répéter la mutation métier lorsqu'un message de
   données déjà enregistrées l'indique. Rétablir les droits et attendre la reprise
   ou redémarrer : un seul _mirror_event_id doit exister dans le fichier cible.
5. Conserver audit_delivery/node_id lors d'une récupération du même profil.
   Ne pas régénérer arbitrairement ce fichier, modifier les demandes réservées
   audit_mirror: ni supprimer les fragments privés de récupération avant examen.
   Le transfert vers un autre profil/poste exige une procédure contrôlée ; un
   autre profil ne reprend pas automatiquement les demandes du poste d'origine.
6. Les fichiers sont des copies du journal central. Un fragment .part préserve
   la fin interrompue pour diagnostic ; le service ne certifie pas la validité
   de tous les anciens fichiers ni ne réécrit en masse les lignes historiques.

LIMITES ET PRIORITÉS RESTANTES

- La clôture est atomique pour les étapes SQL décrites, pas pour l'ensemble des
  fichiers et de MySQL. Les snapshots préalables réussis restent conservés si la
  transaction échoue. Le mécanisme ne constitue pas un verrou global sur les
  écritures de tous les anciens modules, anciens postes ou outils SQL externes.
- Le replay ne reconstruit pas automatiquement les copies manquantes antérieures
  à cette version, qui n'avaient ni identifiant de livraison ni demande persistante.
  Le journal MySQL reste la référence consultable/exportable.
- La génération de documents sans MySQL conserve son repli local existant ; sa
  réimportation centrale automatique hors connexion est un chantier distinct.
  Les interruptions après commit d'un audit en ligne sont couvertes ici.
- Une reprise peut ajouter en fin de fichier un événement horodaté plus ancien ;
  son horodatage d'origine est conservé. L'ordre d'arrivée n'est pas un nouvel
  horodatage métier et le journal central reste prioritaire pour la consultation.
- Une panne matérielle, la durabilité réelle d'un partage SMB et la perte complète
  d'un profil restent à valider dans l'environnement cible. Les tests actuels
  utilisent MySQL et des fichiers locaux jetables, pas deux vrais postes SMB.
- TLS, certains mots de passe MySQL non ASCII, la configuration seule associée
  aux fichiers lors d'une restauration et les appels métier non couverts par
  les comparaisons de clichés restent des lots distincts. Les avertissements
  Qt/Pandas et le profilage volumétrique général restent ouverts.
- Les demandes et fragments contiennent les données des journaux : droits de
  stockage, sauvegarde et rétention restent nécessaires. Ne pas publier leurs
  contenus. Aucun secret réel n'a été lu, affiché ou placé dans ce rapport.
- Les correctifs sont dans les sources. L'ancien exécutable n'inclut pas ces
  protections et aucune nouvelle construction n'a été produite dans ce lot.
