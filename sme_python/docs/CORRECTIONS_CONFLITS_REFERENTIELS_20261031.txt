L22-01 — P1 confirmé — éditions concurrentes des trois catalogues
Emplacements : src/sme_gend/repositories/mysql_bundle_repositories.py:120,
190 et 621 ;
src/sme_gend/repositories/reference_write_guard.py:32.
Avant correction, les UPDATE ciblaient un code ou id sans comparer les champs
présentés à l'utilisateur. Deux lecteurs ouvraient le même grade, structure ou
fonction ; après le premier commit, le second remplaçait ses champs sans conflit.
Pour les fonctions, une édition périmée pouvait aussi propager un ancien libellé
dans les carrières/affectations de façon incohérente avec le catalogue.
Trois tests natifs avant correction échouaient faute de refus du second éditeur.

Correction : jeton opaque (type de catalogue, clé, SHA-256) ajouté aux lignes
chargées. L'empreinte porte sur toutes les colonnes brutes utiles, y compris l'id
interne : grade (id, code, libellé, ordre, effectif), structure (id, code,
désignation, ordre, famille) et fonction (id, libellé). NULL, casse et espaces
restent distingués des valeurs normalisées pour l'affichage. Une suppression
puis recréation du même code avec un autre id est donc détectée.
Le jeton est comparé par SELECT ... FOR UPDATE dans la même transaction que le
DML et la notification du lot 19. Lecture courante, y compris dans un import
REPEATABLE READ dont les SELECT ordinaires voient encore un ancien instantané.
Le verrou reste détenu jusqu'au commit ou rollback réel. Une différence ou une
disparition lève ReferenceConflictError avant mutation et sans nouvelle révision.
L'ancien libellé de fonction doit correspondre au cliché transmis ; le contrôle
précède toute propagation aux carrières/affectations. Leurs SQL restent inchangés.
Référence primaire sur les lectures verrouillantes :
https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/innodb-locking-reads.html
