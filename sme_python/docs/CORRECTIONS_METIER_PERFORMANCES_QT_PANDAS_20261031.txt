L27-01 — P1 confirmé — préconditions d'historique
Emplacements : src/sme_gend/services/dossier_write.py:8
et src/sme_gend/ui/views/conges_view.py:652.
Cause : le service acceptait update/delete sans la ligne affichée, et la fiche
congés omettait effectivement cette ligne. Une ancienne saisie pouvait remplacer
un historique mis à jour sur un autre poste. Le décorateur commun refuse désormais
une version absente avant transaction pour les neuf familles. Les permissions
restent contrôlées avant cette précondition. La fiche congés transmet son événement
affiché et conserve les données saisies si l'enregistrement est refusé.
Le verrou parent, la vérification du propriétaire et la comparaison actuelle sont
préservés. Les API d'ajout restent des intentions explicites ; les imports continuent
d'utiliser leurs chemins dédiés. Aucun algorithme de projection métier n'est changé.
Vérifications : reproduction native avant/après, contrats des 18 update/delete,
formulaire congés succès/conflit, régressions concurrentes des historiques.

L27-02 — P1 confirmé — écriture personnel dans une transaction englobante
Emplacement : src/sme_gend/services/personnel_service.py:21.
Cause : la branche « transaction déjà présente » sortait avant la publication
de synchronisation. Une écriture pouvait être validée sans signal aux autres postes.
Le service rejoint désormais shared_data_write : sauvegarde locale par savepoint,
notification dans la même transaction, invalidation partagée au commit réel.
Un échec pris en charge par l'appelant ne doit pas laisser son insertion partielle
dans la transaction englobante. Une erreur imbriquée dans un lot partagé le fait
échouer entièrement selon le contrat existant. Les lectures locales intermédiaires
sont invalidées également en cas d'annulation. Le noyau transactionnel n'a pas
été réécrit. Les tests natifs vérifient notification et rollback/savepoint.

L27-03 — P1 confirmé — contenu workflow modifié après affichage
Emplacements : src/sme_gend/services/workflow_task_service.py:182

Cause : WHERE status='open' empêchait une seconde résolution, sans vérifier le

Un contenu différent produit un conflit explicite et préserve la sélection à

Tests : contenu périmé, version absente/étrangère, résolution concurrente, échec

L27-04 — P1 confirmé — plan sexe/matricule ancien et absence de notification
Emplacement : src/sme_gend/services/personnel_sexe_reference_sync.py:291.
Cause : application d'UPDATE d'après un rapprochement antérieur, commit direct,
sans comparaison des identités et sans publication de changement.
Les propositions portent maintenant l'empreinte relue et la base d'origine.
Tous les agents sont verrouillés en ordre croissant, par groupes de 250, puis
toutes les versions sont validées AVANT le premier UPDATE. Un agent changé,
supprimé, une version manquante/étrangère ou une proposition dupliquée refuse le
lot complet. Les règles de rapprochement et de saut des conflits sont préservées.
La transaction commune porte données et notification ; un UPDATE réellement sans
effet ne publie rien. Tests natifs de conflit sur la seconde ligne, version étrangère,
agent supprimé, doublons, no-op, transaction externe commit/rollback et second processus.
Ce contrôle concerne le service et ses appelants, pas tous les anciens scripts
ponctuels qui exécutent directement du SQL depuis un CSV.

L27-05 — P1 confirmé — fermeture prématurée et destruction des threads
Emplacements : src/sme_gend/ui/bg_task.py ; ui/views/personnel_list_view.py
et ui/views/liste_present_view.py, sous src/sme_gend/.
Deux reproductions avant correction montrent qu'une fermeture de progression
pouvait rendre None pendant que l'opération continuait. La progression ne se
ferme désormais qu'à la fin réelle du QThread ; la dernière étape n'est pas
assimilée à la fin du travail. Le bouton de fermeture/Escape n'annule pas une
écriture engagée. Les callbacks passent par des QObject avec @Slot et connexion
en file sur le thread GUI, avec durée de vie indépendante de la vue.
Les threads restent retenus jusqu'à finished ; fermer une vue supprime les
callbacks devenus caducs. Les workers de lecture spécialisés sont également
retenus, avec interruption coopérative. Le scan carrière ne supprime plus un
QThread encore actif après l'expiration d'un wait(3000), et la navigation ne
l'attend plus. Un ancien aperçu ne réinitialise plus l'état du rafraîchissement courant.
Une erreur de scan n'est plus convertie en analyse réussie sans alerte : elle
est signalée dans l'interface et le journal sans détail privé.
À la sortie de l'application, les traitements lancés sont attendus, jamais
terminés de force pendant une transaction. Une requête bloquée peut donc prolonger
la fermeture jusqu'à sa fin ou son délai réseau ; aucun gain de ce délai n'est annoncé.
Tests hors écran : progression, succès/erreur sur thread GUI, propriétaire détruit,
callbacks en erreur, libération, arrêt, deux types de workers et résultat périmé.
