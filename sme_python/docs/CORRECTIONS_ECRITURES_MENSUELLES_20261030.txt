L18-01 — P1 confirmé — ordre des paramètres dans les écritures mensuelles
Emplacements : MySQLOrganigramRepository.move_subdivision_to_structure,
attach_subdivision_from_data, rename_subdivision ;
MySQLAgentRepository.backfill_structure_id_for_code, update_structure_column,
rename_subarme_for_structure ; MySQLPadminRepository.update.
Cause : les paramètres du filtre de mois étaient placés en tête du tuple,
avant ceux du SET ou du JOIN, contrairement à l'ordre des marqueurs SQL.
Sans filtre, le tuple vide masquait l'erreur. Avec un mois, des dates et codes
étaient liés aux mauvais marqueurs : erreur MySQL 1292 observée dans les tests.
Correction : ordre JOIN, SET, WHERE conforme à chaque requête, sans modifier les
valeurs, les conditions fonctionnelles, les identifiants ou le paramétrage SQL.
Vérification : périodes septembre et octobre synthétiques ; seul le segment
sélectionné est modifié et les valeurs de carrière du mois voisin sont conservées.
Les cas sans filtre continuent de cibler est_actuelle=1.

L18-02 — P1 confirmé — alias absent pour le renommage des positions
Emplacement : MySQLPadminRepository.update, les deux UPDATE carriere_situation.
Cause : le filtre employait c.est_actuelle / c.sme_periode_id, mais la table cible
ne déclarait pas l'alias c. Erreur MySQL 1054 reproduite, avec et sans filtre.
Correction : déclaration de l'alias sur les deux requêtes ; maintien de la
transaction existante entre les carrières et le référentiel.
Tests : nouveau libellé, options du référentiel et FK corrects ; panne déclenchée
au deuxième UPDATE après modification du libellé et du référentiel : tout est annulé.

L18-03 — P1 confirmé — restriction MySQL 1093 masquée par les erreurs précédentes
Emplacement : config/liste_generale_scope.py, nouveau
carriere_write_scope_for_settings ; adoption dans les seules écritures précitées.
Après correction des paramètres, MySQL refusait encore les requêtes filtrées :
le filtre de lecture contient des sous-requêtes relisant carriere_situation,
qui est aussi la table cible de l'UPDATE. Erreur 1093 reproduite sur 13 scénarios.
Correction : calcul du même filtre dans une table dérivée de clés, matérialisée
par SELECT DISTINCT, puis c.id IN (...). Cette matérialisation empêche la fusion
du bloc dérivé, y compris lorsque derived_merge est activé. Références :
https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/derived-table-optimization.html
https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/update.html
Le filtre de lecture original reste identique. Aucun changement d'optimizer_switch
dans le code applicatif, aucune lecture préalable séparée d'IDs, aucun grand tableau
d'IDs chargé en Python, aucune table ou colonne persistante créée.
Sans filtre mensuel, le prédicat simple existant reste utilisé.
